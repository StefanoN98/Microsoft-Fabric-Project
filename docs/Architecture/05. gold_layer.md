# Gold Layer

> The Gold layer is the business-ready data warehouse layer, where trusted Silver data is transformed into a dimensional model optimized for analytics and reporting. Business logic, KPIs and relationships are consolidated into fact and dimension tables, providing a consistent and governed data foundation for the semantic model and Power BI reporting through Direct Lake.

# Architecture
The Gold loading process follows this logical flow:

1. Read tables from the Silver Lakehouse.
2. Define the Warehouse schemas and table structures.
3. Apply primary key and foreign key metadata where supported.
4. Load dimension tables.
5. Wait for all required dimension loads to complete successfully.
6. Load fact tables using their configured incremental strategies.
7. Expose the resulting semantic model through `SM_GlobalRetail`.

The Warehouse stores the Gold data. 

`GOLD_Pipeline` coordinates the execution of the loading activities; it is not itself a data storage layer.

# Determining SQL Data Types: NB_Define_SQL_Gold_Datatype

Before creating the Gold DDL, a dedicated notebook analyzes every Silver table and proposes an appropriate SQL data type for each column, rather than guessing or defaulting everything to oversized generic types.

The full notebook is available here: [NB_Define_SQL_Gold_Datatype](../../fabric_workspace/03.%20gold_layer/NB_Define_SQL_Gold_Datatype.ipynb)

For every column of every Silver table, the notebook inspects the Spark data type and decides the most sensible SQL equivalent based on what is actually observed in the data:

- **Text columns** proposes a length based on the maximum observed value and a configured safety margin. Values that exceed the configured threshold may require a wider or unbounded text type.
- **Decimal/float columns** are analyzed to determine the actual precision and scale needed, based on the largest value present, which avoids the typical rounding issues that come from blindly using floating-point types for numbers that represent money or quantities.
- **Whole numbers, dates, timestamps, booleans and binary data** map in a fairly direct and predictable way to their SQL equivalents.
- **Unrecognized types** any column whose type cannot be confidently mapped falls back to a safe generic text type, but is explicitly flagged with a warning, so it gets a manual review rather than silently becoming a wrong assumption baked into the DDL.

The notebook also reports useful profiling information:

- Whether a column **contains `NULL`** values and how many were observed.
- Whether the table **contains duplicate** rows based on the comparison performed by the notebook.
- **Warnings for mappings** or data characteristics that require review.

The notebook output includes the original Spark type, proposed SQL type, null counts, duplicate indicators, and warnings. The report is also exported to the Silver Lakehouse for offline review.

## Load type with Stored procedure
Gold tables use different loading strategies according to their purpose and expected behavior. The current design uses full reloads for dimensions and incremental processing for facts.

All table updates are implemented through SQL stored procedures:

<img src="../Images/gold/sp_dwh.png" alt="Bronze Layer Objects" width="1000"/>

### Full (TRUNCATE + INSERT INTO)
Dimension tables (customers, products, suppliers, campaigns, date) are relatively small, slowly-changing reference data. Every time their stored procedure runs, the entire target table is cleared and reloaded from scratch, straight from Silver.

This is a deliberate simplicity choice: for tables of this size, a full reload is cheap and removes an entire category of bugs that incremental logic would introduce (partial updates, missed deletions, out-of-sync historical values). There is no meaningful cost trade-off here, the simplicity of "always start clean" outweighs any theoretical efficiency gain from a more complex incremental approach on data this size.

`dim_date` is a special case within this same "full overwrite" family: instead of being reloaded from a Silver table, it is entirely **generated** as a calendar sequence for a fixed date range, since a date dimension does not need a source system at all. It is pure derived data (day names, week numbers, month names, weekend flags, and similar attributes), so it makes more sense to generate it once for a wide range than to source it from anywhere.

### Incremental (watermark)
Fact tables represent business events or observations that can grow over time. Reloading every fact table in full on each pipeline run can increase execution time and resource consumption as data volume grows.

The current implementation uses incremental loading procedures that identify records to be added to Gold. The exact control depends on the key and date logic implemented for each table.

The documented patterns include:

- **Key-based checks:** identify source records whose business or composite key is not yet present in Gold (es. order_id).
- **Date-based filtering:** restrict processing to a relevant time range, verifying last available date in the Gold table and loading from Silver only   data with dates > last gold table date.
- **Combined checks:** use a date filter to reduce the candidate set (without the necessity to scan the entire table) and a key-based check to avoid inserting records that already exist.

The appropriate pattern depends on the source data, target grain, available timestamps and key definition.

# Pipeline: GOLD_Pipeline
All the stored procedures described above are not run manually or independently, they are orchestrated by a single pipeline, `GOLD_Pipeline`, which enforces the correct execution order.

Dimension tables use an overwrite loading strategy, while fact tables are loaded incrementally. Therefore, all dimension-loading procedures must complete successfully before fact-table processing begins. This sequencing ensures that foreign key (FK) references remain valid and that fact-loading logic can rely on up-to-date dimensional data for joins and lookups.

The pipeline is organized into sequential execution phases, with parallel processing enabled within each phase wherever dependencies allow:
- **Phase 1 Dimensions:** Load all dimension tables running the realted stored procedures and using the overwrite strategy. Stored procedures can run in parallel because there are no dependencies between them.
- **Wait instruction:** acting as an explicit synchronization point; nothing in Phase 2 starts until every dimension load in Phase 1 has completed successfully.
- **Phase 2 Fact Tables:** Once all dimensions are confirmed loaded, every fact-loading stored procedure runs, again in parallel with each other. Facts do not depend on one another either so the same parallelization logic applies here for the same reason

  <img src="../Images/gold/gold_pipeline.png" alt="Bronze Layer Objects" width="600"/>

This approach balances data consistency and referential integrity with execution efficiency through controlled parallelism.

# Semantic Model: Direct Lake
Once the Warehouse is fully populated, a **semantic model** is built directly on top of it using **Direct Lake** mode, and exposed to Power BI as `SM_GlobalRetail`.

All dimension and fact tables from the Warehouse are added to the semantic model and the same relationships already enforced at the database level via foreign keys are recreated as model relationships.

This mirrors the star schema designed at the Warehouse level, so the semantic model is not introducing a new data model, it is just exposing the existing Gold model in a form Power BI can consume interactively.
