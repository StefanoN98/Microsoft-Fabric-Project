# Gold Layer

## Overview

The Gold layer is where cleaned Silver data becomes an actual **business/analytical model**. Unlike Bronze and Silver (both implemented as Lakehouses), Gold is implemented as a **Fabric Data Warehouse** (`WH_Retail`).

This is a deliberate architectural choice, not a stylistic one: Gold hosts a relational, business-modeled **star schema**, with explicit primary keys, foreign keys, and T-SQL stored procedures for loading. A Lakehouse would not enforce referential integrity the same way, and a Warehouse is the natural fit for a model meant to be queried with familiar SQL semantics and consumed directly by a semantic model.

## Fabric Objects

| Object | Type | Purpose |
|---|---|---|
| WH_Retail | Data Warehouse | Hosts the star schema (dimensions + facts) |
| NB_Define_SQL_Gold_Datatype | Notebook | Profiles Silver data to propose optimal SQL data types for Gold DDL |
| GOLD_Pipeline | Pipeline | Orchestrates all stored procedures (dimensions first, then facts) |
| SM_GlobalRetail | Semantic Model (Direct Lake) | Exposes WH_Retail directly to Power BI |

## From Silver to Gold: What Actually Happens Here

Moving data from Silver to Gold is not a simple copy. Three distinct things happen at this stage:

1. **Schema design**: Silver tables (one per source system) are reorganized into a proper **star schema**, grouped into business-domain schemas rather than a single flat namespace
2. **Data type finalization**: every column gets a deliberately chosen SQL data type, sized against real observed data rather than guessed
3. **Load strategy per table type**: dimensions and facts are loaded using two fundamentally different strategies, reflecting their different update patterns (see [Load Strategy](#load-strategy-full-overwrite-vs-incremental-watermark) below)

## Determining SQL Data Types: NB_Define_SQL_Gold_Datatype

Before writing a single line of DDL, a dedicated notebook analyzes every Silver table and proposes an appropriate SQL data type for each column, rather than guessing or defaulting everything to oversized generic types.

### Why not just guess?

A common shortcut in quick projects is to make every text column `VARCHAR(255)` or `NVARCHAR(MAX)` and every number `FLOAT`. This works, but it is a poor practice in a real warehouse: oversized types waste storage and hurt query performance at scale, undersized types cause runtime truncation errors, and generic float types introduce rounding errors on financial or quantity data that should be exact. This notebook exists specifically to avoid that shortcut, by looking at the **actual data**, not just the schema, before deciding a type.

### What the profiling actually checks

For every column of every Silver table, the notebook inspects the Spark data type and decides the most sensible SQL equivalent based on what is actually observed in the data:

- **Text columns** are sized based on the real maximum length found in the data, with a safety margin added on top, rather than being arbitrarily capped. Only if the real content exceeds a reasonable threshold does it fall back to an unbounded text type.
- **Decimal/float columns** are analyzed to determine the actual precision and scale needed, based on the largest value present, which avoids the typical rounding issues that come from blindly using floating-point types for numbers that represent money or quantities.
- **Whole numbers, dates, timestamps, booleans, and binary data** map in a fairly direct and predictable way to their SQL equivalents.
- Any column whose type cannot be confidently mapped falls back to a safe generic text type, but is explicitly flagged with a warning, so it gets a manual review rather than silently becoming a wrong assumption baked into the DDL.

### Data Quality Checks, Reused for Design Decisions

Alongside type mapping, the same notebook also answers two more questions per table, which directly influence the DDL:

- **Does this column actually contain NULLs?** If a column is technically nullable in Silver but never actually contains a NULL value, this is a signal that it could safely become `NOT NULL` in Gold, tightening the model's constraints.
- **Does this table contain duplicate rows?** Comparing total row count against distinct row count flags whether deduplication needs to happen before or during the Gold load, rather than assuming Silver is already perfectly deduplicated.

### Output

For every Silver table, the notebook prints a structured comparison: original Spark type, proposed SQL type, whether NULLs are actually present (and how many), whether duplicates exist at the table level, and any warning notes that deserve a manual look before finalizing the DDL. This full report is also exported to a file, so the type decisions can be reviewed offline before the Gold tables are actually created — data type design is treated as a deliberate step, not an afterthought hidden inside a `CREATE TABLE` statement.

## Schema and Table Design

### Organizing by Business Domain, Not by Source System

Once data types are settled, the next decision is how to organize the Warehouse itself. Rather than dumping every table into a single default schema, tables are grouped into four schemas, each representing a business domain rather than a source system:

| Schema | Contains |
|---|---|
| _Shared_Dim | dim_customers, dim_products, dim_date |
| _Transactions | fact_orders, fact_orders_details |
| _Supply_Chain | fact_inventory, dim_suppliers |
| _Marketing | dim_campaign, fact_order_campaign, fact_web_logs, fact_reviews |

This distinction matters: a source-system-oriented schema (e.g. "CRM schema", "ERP schema") would leak implementation details from earlier layers into the business model. A domain-oriented schema instead reflects how the business actually thinks about the data — customers and products are shared concepts used across the whole company, while transactions, supply chain, and marketing are separate concerns with their own facts.

### Dimension vs Fact: Two Different Roles

Every table in Gold is either a **dimension** (descriptive, relatively static entities such as customers, products, dates, suppliers, campaigns) or a **fact** (transactional, growing-over-time records tied to business events, such as orders, inventory snapshots, reviews, or web activity). This distinction is not just naming convention — it directly determines how each table gets loaded later, since dimensions and facts follow two very different loading strategies (see [Load Strategy](#load-strategy-full-overwrite-vs-incremental-watermark)).

### Merging Multiple Silver Sources into a Single Entity

One of the responsibilities that belongs specifically to Gold — not Silver — is deciding when multiple Silver tables actually represent the same business entity and should be merged into one.

The clearest example in this project is `dim_products`: product master data originates from two different Silver tables coming from two different source systems — the ERP export (core product attributes such as name, category, price, supplier) and the GitHub-sourced product catalog (color, warranty, weight, images). From a source-system point of view these are two unrelated tables; from a business point of view they describe the exact same product, and a business user querying "tell me everything about this product" should not need to know that the data originally came from two different systems. Gold merges them into a single `dim_products` table, joined on the shared product identifier.

This kind of merge decision — recognizing that two technically separate Silver tables are conceptually one entity — is a defining characteristic of the Gold layer, and is exactly the kind of business modeling that Bronze and Silver deliberately avoid doing.

### Dropping Technical Columns

Audit columns introduced in Bronze and Silver for lineage tracing (ingestion timestamps, source file names) are dropped when a table reaches Gold. They serve a purpose during ingestion and cleaning — tracing where a record came from and when it entered the pipeline — but they are not part of the business model itself, and including them in Gold would only add noise for anyone querying or reporting on the data.

### The Resulting Model

Conceptually, the Gold model forms a classic star schema, with `fact_orders` acting as the central fact table connecting most other entities, either directly or transitively:

    dim_customers ---------- fact_orders ---------- fact_orders_details ---------- dim_products (merged: ERP + product_catalog)
                                  |                                                        |
                                  +---- fact_order_campaign ---- dim_campaign              |
                                  |                                                        |
                                  +---- fact_reviews --------------------------------------+

    dim_suppliers ---- (SupplierID) ----> dim_products
    fact_inventory ---- (ProductID) ----> dim_products

    fact_web_logs ---- (CustomerID, ProductID) ----> dim_customers / dim_products

    dim_date ---- (OrderDate) ----> fact_orders

Every fact table connects back to one or more dimensions via foreign keys, which are enforced at the database level once all tables exist — referential integrity is treated as a first-class requirement of the Gold model, not an optional nice-to-have.

## Load Strategy: Full Overwrite vs Incremental Watermark

Dimensions and facts are not just structurally different — they are also loaded using two fundamentally different strategies, each matched to how that type of table actually changes over time.

### Dimensions: Full Overwrite

Dimension tables (customers, products, suppliers, campaigns, date) are relatively small, slowly-changing reference data. Every time their stored procedure runs, the entire target table is cleared and reloaded from scratch, straight from Silver.

This is a deliberate simplicity choice: for tables of this size, a full reload is cheap and removes an entire category of bugs that incremental logic would introduce (partial updates, missed deletions, out-of-sync historical values). There is no meaningful cost trade-off here — the simplicity of "always start clean" outweighs any theoretical efficiency gain from a more complex incremental approach on data this size.

`dim_date` is a special case within this same "full overwrite" family: instead of being reloaded from a Silver table, it is entirely **generated** as a calendar sequence for a fixed date range, since a date dimension does not need a source system at all — it is pure derived data (day names, week numbers, month names, weekend flags, and similar attributes), so it makes more sense to generate it once for a wide range than to source it from anywhere.

### Facts: Incremental Watermark

Fact tables (orders, order details, inventory, order-campaign attribution, web logs, reviews) behave completely differently: they grow continuously and can become very large over time. Reloading them entirely on every run would be wasteful and, at a certain scale, simply impractical.

Instead, fact tables use a **watermark pattern**: every load remembers a reference point marking "everything up to here has already been loaded", and only processes records newer than that reference point on the next run. In practice, the watermark is read directly from the destination table itself — the load procedure checks the most recent value already present in Gold, and only pulls records from Silver that come after it. This keeps the pattern simple, at the cost of one explicit assumption: this approach only works correctly for append-only sources, where existing historical rows are never updated or deleted after being written. If a source system started modifying old records after the fact, this pattern would need to evolve into something more sophisticated (e.g. a dedicated tracking table, or full change-data-capture).

### Why a Date Alone Is Not Always Enough

A subtlety worth calling out explicitly: for `fact_orders`, the natural watermark candidate is the order date. However, order dates in this dataset are stored at day-level granularity — multiple distinct orders can share the exact same date value. A watermark based purely on "load everything strictly after the last date" would silently skip orders that arrived later on the same day as the last successfully loaded batch, since their date would be equal to, not greater than, the watermark.

The load logic accounts for this by combining two checks together: a broad filter on the date (to avoid scanning the entire historical Silver table on every run) followed by a precise check against the unique order identifier, to make sure no order sharing the watermark's date gets silently skipped. This two-step combination is what makes the watermark both efficient (thanks to the date filter) and safe (thanks to the identifier check).

### Composite Keys for Some Fact Tables

Not every fact table has a single natural unique identifier. Several of them are only uniquely identified by a **combination of columns**:

- Order line items are uniquely identified by the combination of order and line item, not by either one alone
- Inventory records are uniquely identified by the combination of warehouse and product
- Web log events are uniquely identified by the combination of session and product

For these tables, the same watermark logic applies conceptually, but the "has this record already been loaded" check has to compare the full combination of key columns together, rather than a single identifier — checking only one of the two columns would incorrectly treat genuinely different records as duplicates, or vice versa.

### Summary

| Table Type | Strategy | Reasoning |
|---|---|---|
| Dimensions (customers, products, suppliers, campaigns) | Full Overwrite | Small, slowly-changing, simplicity outweighs efficiency at this scale |
| dim_date | Full Overwrite (generated) | Pure derived data, no source system needed |
| Facts with a single natural key (orders) | Incremental Watermark + key check | Large, append-only, needs both efficiency and correctness |
| Facts with a composite key (order details, inventory, web logs) | Incremental Watermark + composite key check | Same as above, but uniqueness requires more than one column |

## Orchestrating the Load: GOLD_Pipeline

All the stored procedures described above (one per dimension, one per fact table) are not run manually or independently — they are orchestrated by a single pipeline, `GOLD_Pipeline`, which enforces the correct execution order.

### Why Order Matters Here

Fact tables reference dimensions through foreign keys, and in some cases the loading logic itself may implicitly rely on dimensions already being current. Running fact loads before dimension loads would risk foreign key violations or referencing stale dimension data. For this reason, the pipeline is structured in two distinct phases rather than firing every stored procedure at once.

### Phase 1: Dimensions, in Parallel

All dimension-loading stored procedures run **in parallel** with each other, since dimensions are independent of one another (customers do not depend on products, campaigns do not depend on suppliers, and so on). Running them in parallel rather than sequentially reduces total execution time with no downside, since there is no dependency to protect.

A **Wait** step follows this phase, acting as an explicit synchronization point: nothing in Phase 2 starts until every dimension load in Phase 1 has completed successfully.

### Phase 2: Facts, in Parallel

Once all dimensions are confirmed loaded, every fact-loading stored procedure runs, again in parallel with each other. Facts do not depend on one another either — `fact_orders` loading does not need `fact_inventory` to be loaded first — so the same parallelization logic applies here for the same reason: no dependency, no need to serialize.

### The Resulting Flow

    Phase 1 (parallel): dim_customers, dim_products, dim_date, dim_suppliers, dim_campaign
        |
        v
    Wait (synchronization point)
        |
        v
    Phase 2 (parallel): fact_orders, fact_orders_details, fact_inventory,
                         fact_order_campaign, fact_web_logs, fact_reviews

This two-phase, parallel-within-phase structure gives the fastest possible execution time that still respects the one hard dependency in the model: dimensions must exist and be current before facts that reference them are loaded.

## Semantic Model: Direct Lake

Once the Warehouse is fully populated, a **semantic model** is built directly on top of it using **Direct Lake** mode, and exposed to Power BI as `SM_GlobalRetail`.

### Why Direct Lake

Direct Lake is what makes this final step meaningfully different from a traditional BI setup: instead of importing a copy of the data into the semantic model (as a classic Import mode model would), Direct Lake reads data straight from the Warehouse's underlying storage. This means there is no duplicated dataset to keep in sync, no scheduled refresh job required to reflect new data, and the model stays current with whatever is in `WH_Retail` at query time.

### Building the Relationships

All dimension and fact tables from the Warehouse are added to the semantic model, and the same relationships already enforced at the database level via foreign keys are recreated as model relationships:

- `dim_customers` connects to `fact_orders`, `fact_web_logs`, and `fact_reviews`
- `dim_products` connects to `fact_orders_details`, `fact_inventory`, and `fact_web_logs`, and also to `dim_suppliers` (since every product has a supplier)
- `dim_date` connects to `fact_orders` via the order date
- `dim_campaign` connects to `fact_order_campaign`, which in turn connects to `fact_orders`
- `fact_orders` acts as the central hub, also connecting to `fact_orders_details` and `fact_reviews`

This mirrors the star schema designed at the Warehouse level almost one-to-one — the semantic model is not introducing a new data model, it is simply exposing the existing Gold model in a form Power BI can consume interactively.

## End-to-End Orchestration: ORCHESTRATION_PIPELINE

A single top-level pipeline ties every layer together into one repeatable, end-to-end execution: `ORCHESTRATION_PIPELINE` triggers, in strict sequence, the ingestion pipeline into Bronze, the transformation pipeline into Silver, the loading pipeline into Gold, and finally a refresh of the semantic model.

    Invoke Pipeline: PL_INGEST_ADLS      (Bronze ingestion)
        |
        v
    Invoke Pipeline: Silver_Pipeline     (Bronze -> Silver transformation)
        |
        v
    Invoke Pipeline: GOLD_Pipeline       (Silver -> Gold loading)
        |
        v
    Semantic Model Refresh: SM_GlobalRetail

Each stage only starts once the previous one has fully succeeded, since every layer depends on the one before it being complete and correct — there is no reason to attempt a Silver transformation on a Bronze ingestion that failed halfway through, nor to load Gold from a Silver layer that never finished updating.

This single pipeline is effectively the "run everything" button for the whole platform: triggering it end-to-end takes raw source data all the way through to a refreshed, reportable semantic model, with no manual intervention required at any intermediate step.
